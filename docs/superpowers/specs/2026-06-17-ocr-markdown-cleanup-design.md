# OCR Markdown 格式梳理 Design Spec

**目标**：清理 `site/` 下由 OCR 转换得到的 34 个 markdown 文件中，因 PDF 分页和 OCR 识别引入的格式与排版问题。仅调整格式与排版，不动原文文字。

**执行方式**：大模型基于语义和上下文逐文件判断修改，不使用脚本、不套正则规则。

**仓库**：`wyxpku/power-trading-docs`，分支 `main`。

---

## 1. 改动范围与边界

### 1.1 处理对象

仅 `site/` 下的 34 个 markdown 文件：

- `site/index.md`
- `site/ch01/index.md` ~ `site/ch31/index.md`（31 章）
- `site/appendix-a.md`、`site/appendix-b.md`

总规模约 15,000 行，含约 630 处 `<PageDivider pdf-page="..." />` 标记。

**D 类（章节边界错位）补充发现（2026-06-17）**：试点过程中发现 `chapter_mapping.json` 的页码范围有偏移，导致若干章节的开头被放在了前一章的末尾。已确认错位边界：ch12/ch13、ch14/ch15、ch15/ch16、ch19/ch20、ch20/ch21。详见 §3.4。

### 1.2 不动的范围

- `docs/`（原始 PDF 和历史 specs/plans）
- `scripts/`（转换脚本已是死代码，独立处理）
- `assets/pages/`（扫描图 PNG）
- VitePress 配置、Vue 组件（`PageDivider.vue`、`ScanViewer.vue`）
- 所有图片路径（`![...](/pages/crops/...)`）
- frontmatter（`title:` 行）
- `<PageDivider>` 的 `pdf-page` 数值（页码元数据必须保留）
- 表格 HTML 结构（`<table>`、`<tr>`、`<td>` 的骨架不变）

### 1.3 内容修改的边界

**绝不擅自动原文文字**。遇到以下情况**单独列清单**交用户确认：

- OCR 明显错字（如"已"↔"己"、"未"↔"末"）
- 标点全半角不一致（中文上下文里混了半角逗号）
- 数字/单位明显错误（如 "GW" 误作 "Gw"）

格式类调整（空格、全半角标点统一、字面 `\n` → `<br>`、空行调整）**直接改**，不算内容修改。

## 2. PageDivider 的处理原则

### 2.1 组件现状

`site/.vitepress/theme/PageDivider.vue` 渲染为：

```html
<div class="page-divider" id="page-div-N" data-page="N"></div>
```

CSS 仅有 `position: relative`，**视觉上完全不可见**（无边框、无高度、无背景、无页码 badge）。原设计文档描述的"thin horizontal divider with page number badge"并未实现。

### 2.2 ScanViewer 用法

`site/.vitepress/theme/ScanViewer.vue:38-60` 使用 `IntersectionObserver`（`rootMargin: '-80px 0px -50% 0px'`）监听所有 `.page-divider` 元素，当某 divider 进入视口上部区域时，读取其 `data-page` 属性切换右侧扫描图面板。

**PageDivider 的唯一实际作用**：为 ScanViewer 提供 PDF 页码元数据 + 滚动定位哨兵。

### 2.3 设计原则

**PageDivider 只保存原始 PDF 页面元数据，不影响排版**。

实现方式：根据所处上下文采用两种放法。

#### 2.3.1 内联放法（A 类场景，处于同一段落的两片段之间）

**实测结论（2026-06-17）**：必须把 PageDivider 和前后文本放在**同一行**，否则 markdown-it 会把它当块级元素切断段落：

```md
...不涉及电力 <PageDivider pdf-page="21" /> 实物商品的交割...
```

（一整行，不要换行）→ 渲染为一个 `<p>`，`<span class="page-divider">` 嵌在中间，ScanViewer 仍能用 data-page 同步。

注意：此放法会让源文件出现超长行（合并段落全部内容 + 中间的 PageDivider 在一行）。这是实现真内联渲染的必要代价。

#### 2.3.2 块级放法（天然块边界）

PageDivider 处于标题之间、图与文之间、本就是两个不同段落之间时，**保留周围空行**，维持块级。前后本来就是不同块，不存在"切段"问题。

### 2.4 组件层面的可能调整

**已实施（2026-06-17）**：`<div>` 嵌在 `<p>` 里是非法 HTML。实测发现 markdown-it 把任何**行首**的 `<Tag` 都当块级处理，无论周围有没有空行、前导空格、还是把 `<div>` 改成 `<span>`。**唯一能实现真内联的放法是把 PageDivider 和前后文本放在同一行**：

```md
text-before <PageDivider pdf-page="N" /> text-after
```

为此 `PageDivider.vue` 已改为渲染 `<span>`（保持 `position: relative`，IntersectionObserver 对 span 同样有效）。**A 类内联放法相应改为单行放法**：把跨页段落的两个片段和中间的 PageDivider 合并到同一行。代价是源文件中合并段落变成超长单行（部分段落 1000+ 字符），但这是实现"PageDivider 不影响排版"目标的唯一途径。

## 3. 三类问题的判定与改法

所有判定均由大模型基于上下文语义完成，不使用正则规则。

### 3.1 A 类：跨页段落合并

**判定**：读完 PageDivider 前后的两个文本块，若语义上是同一自然段（前段结尾非句号/问号/叹号且话题紧密延续，或即便有标点但话题延续），则合并。

**改法**：采用 §2.3.1 的内联放法（**单行**：text-before + PageDivider + text-after 全在一行）。

```md
前段（结尾通常是逗号、或句子未完）

<PageDivider pdf-page="N+1" />

后段（承接前段）
```
→
```md
前段（结尾通常是逗号、或句子未完） <PageDivider pdf-page="N+1" /> 后段（承接前段）
```

**不合并的反例**：前段以完整句号结尾、且后段是新话题起头（即便跨页）→ 保留两段，PageDivider 维持块级（§2.3.2）。

### 3.2 B 类：标题层级修正

**判定**：编号子项（`## 1. xxx`、`## 2. xxx`）出现在更深的父节之下，层级与上下文不匹配。

**改法**：根据父节层级推断正确层级。

示例 1（`site/appendix-a.md`）：
```md
## A.2.1.2 市场概述     ← H2
## 1. 市场模式          ← 当前 H2，但父节是 H2，应为 H3
## 2. 价格机制          ← 同上
```
→ `## 1. 市场模式` 改为 `### 1. 市场模式`。

示例 2（`site/ch15/index.md:81`）：
```md
#### 15.1.4.1 基础情况    ← H4
## 1. 发电侧上网电价      ← 当前 H2，应为 H5
```
→ `## 1. 发电侧上网电价` 改为 `##### 1. 发电侧上网电价`。

**边界**：若编号项实质上是普通列表项而非独立小节（语义判断），降为**加粗段落** `**1. xxx**` 而非标题。拿不准的列入清单问用户。

### 3.3 C 类：表格单元格多行

**判定**：HTML `<table>` 的 `<td>` 内含字面 `\n` 文本（HTML 中不渲染为换行）。

**改法**：`\n` → `<br>`。

示例（`site/ch13/index.md:14`）：
```html
<td>(1) 接入 500kV 电网的常规火电机组。\n(2) 部分 30 万 kW 常规火电机组</td>
```
→
```html
<td>(1) 接入 500kV 电网的常规火电机组。<br>(2) 部分 30 万 kW 常规火电机组</td>
```

**边界**：若 `\n` 出现在不需要换行的位置（如空格误识别），直接删除。若单元格内容本应拆为多行而 `<br>` 也不够，列入清单问用户。

### 3.4 D 类：章节边界错位（2026-06-17 补充）

**判定**：ch(N) 文件末尾出现了 ch(N+1) 的开头内容（章节标题、Part 标题、ch(N+1) 的正文段落、`N+1.X` 小节）。根因是 OCR 转换时 `chapter_mapping.json` 的页码范围有偏移，把 ch(N+1) 的前几页错记到了 ch(N) 名下。

**已确认的错位边界**：

| 边界 | 错位内容 |
|---|---|
| ch12 → ch13 | `# 第三篇 国内实践篇` + ch13 章标题 + 13.1/13.1.1/13.1.1.1/13.1.1.2 |
| ch14 → ch15 | ch15 章标题 + 15.1/15.1.1/15.1.1.1 |
| ch15 → ch16 | 16.1.1.2/16.1.1.3/16.1.2/16.1.3 |
| ch19 → ch20 | ch20 章标题 + 20.1/20.1.1/20.1.1.1/20.1.1.2 |
| ch20 → ch21 | `# 第四篇 技术支持系统篇` + ch21 章标题 + 21.1/21.1.1 |

**干净的边界**（无需处理）：ch13/ch14、ch16/ch17、ch21/ch22 等。

**改法**：
1. 在 ch(N) 文件中找到**最后合法的 ch(N) 行**（通常是 `N.X 本章小结` 段落的结尾），其后的所有内容（包括 PageDivider、Part H1、ch(N+1) 章节标题、ch(N+1) 段落和小节）属于 ch(N+1)。
2. 将这些内容从 ch(N) 文件**剪切**（删除）。
3. **粘贴**到 ch(N+1) 文件的 frontmatter 之后、现有第一行 PageDivider 之前。
4. 保留所有原文和 PageDivider 的 `pdf-page` 数值不变。
5. 粘贴后，ch(N+1) 文件原本开头若是承接半句（如 ch13 文件开头 "部制电价模式…" 承接 ch12 末尾 "…改为全电量竞争、两"），它和被剪切过来的末尾之间会形成一个 A 类场景（跨 pdf-page 的段落切断），**留给 ch(N+1) 的 within-file 清理阶段处理**，不在 D 类阶段合并。

**为什么不顺手合并**：保持 D 类纯粹做"跨文件搬移"，A 类做"段内 PageDivider 内联"。两类职责清晰、易于审查。

## 4. 执行流程

### 4.1 单文件处理流程

每个文件都走以下步骤：

1. **通读**：完整 `Read` 整个文件，建立上下文（不能只看片段就改）
2. **诊断**：标记所有 A/B/C 候选点，**写进临时清单**（先不改），交用户过目
3. **修改**：用户确认清单后，逐项 `Edit`，每个 Edit 精准对应一处
4. **自检**：改完重读整个文件，确认未破坏其他排版（frontmatter、图片路径、`pdf-page` 数值、表格 HTML 结构）
5. **本地预览**（仅试点阶段）：`cd site && npm run docs:dev`，浏览器翻一遍，重点验证 PageDivider 内联放法渲染正常、ScanViewer 滚动同步仍工作
6. **提交**：单文件 commit

### 4.2 兜底

试点过程中如发现第四类问题（列表缩进、引用块、代码块异常等），**不擅自扩大范围**，先加进清单问用户。

## 5. 提交粒度与节奏

### 5.1 试点阶段（3 个文件）

- 试点文件：`site/ch01/index.md`、`site/ch13/index.md`、`site/appendix-a.md`
- 选择理由：
  - `ch01`：A 类（跨页段落）+ B 类（编号子项被识别为 `##`），400 行规模适中
  - `ch13`：A 类 + C 类（26 处 table 标签，本文件即有 `\n` 字面文本案例）
  - `appendix-a`：B 类重灾区（大量 `## 1. xxx`、`## 2. xxx` 嵌在 A.2.x.x 节下）+ A 类，777 行
- 每个文件一个 commit（共 3 个 commit），方便单独回滚
- 提交信息格式：`docs: cleanup OCR formatting in site/ch01/index.md`

### 5.2 全量阶段（剩余 31 个文件）

试点验收通过后，按"每文件一 commit"节奏推进。复杂文件（如表格密集的 ch10、ch11）可拆成"段落合并"和"表格修复"两个 commit。

---

## 6. 试点退出标准

3 个试点文件改完后，需满足以下全部条件才算"规则定稿"：

1. 三类问题（A/B/C）在每个试点文件里都出现过至少一次并被正确处理
2. `npm run docs:dev` 本地预览：段落合并生效、PageDivider 内联渲染无异常、ScanViewer 滚动同步正常
3. 用户逐文件 diff 过目并确认
4. 形成一份"规则备忘录"（追加到本 spec 末尾），作为后续 31 个文件的参考

## 7. 范围与非目标

### 7.1 在范围内

- `site/` 下 34 个 markdown 文件的格式与排版修复
- A/B/C 三类问题的语义判定与修改
- PageDivider 在 markdown 源层面的内联/块级放法调整
- 必要时 `PageDivider.vue` 组件 `<div>` → `<span>` 的小调整（待试点定）

### 7.2 不在范围内

- 重新跑 OCR 或修改 OCR 转换脚本
- 修改原文文字内容（明显错字单独列清单交用户确认）
- VitePress 配置、ScanViewer 组件的改动
- 性能优化、SEO、可访问性
- 移动端适配
